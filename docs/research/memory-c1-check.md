# C1: надёжное хранилище памяти

Дата: 2026-10-30. Выполнен только подэтап C1 из [разбивки этапа C](../plans/03-memory-stages.md). Хранилище программно работает на синтетических данных; экран памяти, подстановка в чат, извлечение фактов и перенос старой БД не подключены.

## Реализация

Новый независимый пакет `packages/memory` использует версионированный JSON snapshot `memory.json`, существующие Zod и OperationResult, без новой зависимости и копирования кода persistent-memory. Диск ограничен 8 MiB и 10 000 записей; content — 16 000 символов. Снимок содержит проверяемую структуру и checksum. Checksum обнаруживает повреждение данных, но не является подписью или подтверждением истинности факта.

Изменения сериализуются. Запись выполняется в новый временный файл, затем fsync и atomic rename; RAM обновляется после успешной фиксации. Ошибка не возвращает «сохранено», а очередь остаётся пригодной для следующей операции. Это полнофайловый snapshot, не транзакционная SQLite-база и не измеренная высокопроизводительная система.

До создания каталога на Windows нормализуется путь, проверяются DriveInfo и canonical существующего предка; UNC и Network/Unknown-диски отклоняются. На Windows владелец держит отдельный named pipe по canonical пути каталога. ОС освобождает его при аварийном завершении; PID-файл не приходится удалять вслепую. На других ОС используется exclusive lock-файл с консервативным отказом после аварии; автоматическое восстановление этого lock-файла не реализовано. Целевая подтверждённая платформа C1 — Windows.

Записи имеют устойчивый ключ темы внутри области, ID и revision. Изменение, удаление и явное возвращение забытого факта требуют ожидаемую revision. Забытая запись оставляет пустую tombstone для защиты от повторного создания со старым ключом; её текст, теги и metadata очищаются. Возвращение — отдельный явный revive с сохранением ID и новой revision.

Все новые записи в C1 создаются явным действием с manualPriority=true. Background API захватывает ID/revision одноразовым токеном; поздний результат даёт CONFLICT, актуальный — CONFIRMATION_REQUIRED. Он не создаёт записи и не записывает новое значение. Так поздний результат не может отменить ручную правку или вернуть старый вариант под новым ID через автоматический API. Смысловые дубли с произвольно выбранными разными ключами не распознаются: связь с устойчивым ключом должна обеспечиваться будущим сценарием предложений C4, а не обещаться по сравнению текста.

Session-записи и ожидающие background-токены живут только в RAM и не входят ни в snapshot, ни в backup. После close чтение и новые записи закрыты, RAM-кэш очищен. Перед восстановлением собственного backup записывается копия текущего постоянного состояния; успешное восстановление повышает revision, инвалидирует токены и очищает session. Повреждённая основная копия останавливает открытие; автоматического возврата к старому snapshot нет, чтобы не воскресить забытые факты. Отдельный инструмент восстановления повреждённого файла не входит в C1.

## Проверки

Проверки выполнялись на Node 24.22.1 / Windows с доступом к локальным файловым операциям и named pipes. Личные БД, чаты и настройки не читались; LM Studio, генерация и модели для C1 не вызывались.

| Проверка | Результат |
|---|---|
| CRUD → close → повторное открытие | Сохранено последнее подтверждённое состояние |
| Два владельца одного каталога | Второй получает отказ |
| 12 одновременных созданий, два редактора одной revision | Очередь сохраняет все создания; только одна конфликтующая правка проходит |
| Инъекция ENOSPC до rename | WRITE_FAILED; прежние RAM и файл не меняются, следующая запись работает |
| Настоящий kill дочернего процесса до commit | Прежняя запись сохранена, новый владелец открывается |
| Настоящий kill после успешного commit | Новая запись сохранена, lease освобождён ОС |
| Session → постоянная запись → snapshot/backup → restart | Session-маркер не появляется в файле/backup и исчезает после restart |
| Поздний background, replay, свежий background после ручной правки | CONFLICT / INVALID_TOKEN / CONFIRMATION_REQUIRED; ручной факт остаётся единственным |
| Delete → restart → попытка save со старым ключом → explicit revive | Нет автоматического возврата; explicit revive сохраняет ID и повышает revision |
| Backup/restore metadata и старого содержимого | Совместимые поля сохранены; revision растёт, прежние токены недействительны |
| Отказ restore | Текущие записи, session, revision и актуальные токены сохраняются |
| Неудачная инициализация → повтор | Владение освобождено, повтор работает |
| Повреждение snapshot/backup, чужой backup, hardlink | Явный отказ без сброса или изменения исходного файла |
| Closed reads и слишком большой content | Явный отказ |

Начальный тестовый набор упал с отсутствующим модулем, затем прошёл. Отдельно воспроизведён RED чтения session из закрытого владельца; исправлено отказом чтения и очисткой кэша.

Независимое ревью выявило один P2: начальная проверка допускала UNC с прямыми слешами, а локальный named pipe не защищает общий файл между двумя компьютерами. RED → GREEN исправлено валидацией нормализованного пути, типа диска и canonical пути до владения хранилищем. Альтернативный синтаксис и Network/Unknown проверены без обращения к SMB; сетевые папки и mapped drives для теста не создавались. Других подтверждённых существенных замечаний ревью нет.

## Границы

- Process-kill тесты не доказывают сохранность при физическом отказе диска или отключении питания. Подтверждена атомарность на локальной файловой системе при аварии процесса.
- «Забыть» убирает активный факт и его содержимое из текущего snapshot. Ранее явно созданные backup и старые чаты могут содержать прежнее значение; они не переписываются и не являются обещанием безопасного стирания носителя.
- Restore — явное возвращение старого состояния, способное вернуть ранее удалённый факт по решению пользователя. Автоматический background этого не делает.
- Нет импорта SQLite/sql.js старого плагина, управления его живой БД, проверки устойчивого chatScopeId, межпроцессного HTTP API или интерфейса. Эти работы остаются C2–C5.
- Пока модуль не подключён к host, данные действующей установки Companion остаются прежними. Никакое автоматическое переключение плагинов памяти не выполнялось.
