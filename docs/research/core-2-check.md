# CORE-2 — сохранение общей заметки через текущую LLM

**Дата:** 1 ноября 2026. **Состояние:** реализация и автоматические проверки готовы; пользователь подтвердил нативное сохранение и видимость записи в панели. Сохранность после перезапуска панели также подтверждена пользователем; остальные нативные сценарии ещё не подтверждены. CORE-3 не начат. Документы D4/D5 и советник не развивались.

Основа: HEAD `5016b64`, ветка `codex/memory-feedback-and-priorities`, существующий PR №9. Коммиты: `b25622a` — план, `3b30bde` — атомарные операции, `e0aec21` — канал, `6334e27` — интеграция LLM, `345d7b0` — проверка пробелов в квитанции. Итоговая документация фиксируется отдельно.

## Результат реализации

- В выбранном чате включается «Запоминание по просьбе». Текущая LLM последовательно разбирает обычное намерение и точный доступный текст, затем вызывает `companion_remember_note`. Ни вторая модель, ни вложенная конкурирующая генерация не используются.
- Разрешением служит текущая прямая просьба. Код проверяет дословный фрагмент вне обычных цитат/блоков/inline-кода и наличие текста в доступном сообщении. Неопределённый материал/карточки не проходят как личный факт; неоднозначность даёт уточнение. Отрицание и понимание произвольных пересказов проверяются смысловым разбором LLM, а не перечнем русских команд.
- Host выдаёт разрешение на конкретный operationId/текст/ревизию. Ревизия запрашивается **до** работы LLM, поэтому ручная правка во время разбора не обходится поздней записью. Разрешение живёт 120 секунд. Перед первым расширением снимка сам владелец создаёт `before-core2-*.json`.
- Один владелец фиксирует факт и квитанцию одним атомарным снимком. Повтор того же ID с теми же аргументами возвращает проверенный результат; другие аргументы дают конфликт. Проверяется фактическая активная редакция: повтор после ручной правки/удаления не восстанавливает старое и не подтверждает его как актуальное.
- Прямое сохранение не создаёт предложение. Старый capture/очередь предложений и ручные операции панели сохранены. Автоматического немедленного сохранения нет.
- Свободный текст LLM в ходе записи не показывается: итог формирует Core из проверенной квитанции. При потерянном ответе проверяется ID операции без повторной записи. Отказ, ошибка, отмена до отправки и неизвестный результат различаются. Stop после фиксации не означает откат; если квитанция получена, показывается реальная запись.
- Для случая пропущенного намерения обычный ответ буферизуется и проходит отдельную смысловую проверку той же LLM. Невалидная/недоступная проверка или неподтверждённое заявление об успехе дают сообщение Core об отсутствии изменения. Инструменты и их разрешения остаются видимыми; свободный текст показывается после проверки.
- Новый факт виден через **тот же GET API**, который использует панель; проверено реальным owner/channel/API и повторным открытием хранилища. Личные записи и живое хранилище не использовались.

## Исправление после первого нативного теста

Первый тест пользователя на `0.1.0-core2` завершился отказом и пустым списком панели. Read-only запрос к работающему каналу подтвердил доступность владельца и revision 0; секрет подключения и содержимое личной памяти не выводились.

Воспроизведение через SDK на уже загруженной `gemma4-12b-qat-uncensored-hauhaucs-balanced` с вымышленной просьбой и отдельным временным owner показало причину: `content` содержал 6231 символ вместе с рассуждением/служебным маркером, тогда как `nonReasoningContent` содержал корректный конечный JSON. Разбор `JSON.parse(result.content)` отвергал ответ до вызова сохранения. Прежние тестовые ответы имели упрощённую форму без этих полей.

В `0.1.1-core2`, revision 4, оба служебных разбора используют существующий `extractPayload`: итоговый текст без рассуждения. Пустой итог не подменяется JSON из рассуждения. Пять регрессионных тестов сначала упали, затем прошли: конечный JSON при загрязнённом общем поле, пустой итог с JSON только в рассуждении, корректная стадия ошибки, приоритет окончательного запрета в проверке ответа и разрешение безопасного конечного ответа. Ошибки подготовки/генерации/разбора/канала теперь различаются без вывода сырого текста модели.

Повторная SDK-проверка после исправления прошла на той же уже загруженной модели: распознана просьба, LLM вызвала инструмент, временный owner сохранил одну заметку, после закрытия/повторного открытия сохранился тот же ID. Полный цикл занял около 3½ минут, без автоматических повторов. Реальная общая память панели не изменялась. Использовался тестовый controller с вымышленной историей, а не открытый чат LM Studio.

Исправление: коммит `0a78207`. Обновление остаётся внутри CORE-2. После обновления пользователь прислал два скриншота: `/core` показывает `0.1.1-core2`, запоминание включено; просьба «Запомни, что проверочная метка — МАЯК-731.» завершилась квитанцией с ID/редакцией 1. Панель после «Обновить список» показывает одну общую запись с тем же текстом. Это подтверждает нативный путь просьба → запись владельца → видимая память. Затем по просьбе перезапустить панель и проверить список пользователь сообщил «На месте»: сохранность записи после restart подтверждена. Остальные сценарии остаются открытыми.

## Цитата и согласование обычного ответа

Пользователь подтвердил отрицание: «Не сохраняй это: проверочная метка — ТУМАН-509.» не создало запись. Следующая проверка, объяснение цитаты про ИНЕЙ-604, показала статус отсутствия изменения памяти, но весь обычный ответ был скрыт защитой. Сам факт нормального объяснения на этом шаге не принят.

Изолированная проверка на безопасном подготовленном объяснении прошла: фильтр не запрещает все цитаты. Воспроизведение полного entry handler на текущей Gemma и вымышленной истории выявило конкретную причину: предварительный разбор вернул `intent=none`, а основной ответ назвал цитату новой инструкцией и объявил две активные метки. Классификатор вернул `reportsSuccess=true` и правильно скрыл этот ответ. В этом диагностическом запуске кэш был только в RAM, путь канала — заведомо отсутствующий; пользовательские чаты/записи не читались.

В `0.1.2-core2`, revision 5, обычная генерация получает проверенный результат «в этом ходе память не изменялась» в служебной преамбуле. Это тот же результат управления ходом, а не команда из истории. Исходные SDK-сообщения не изменяются, новая преамбула не записывается в чат и учитывается обычным бюджетом handler. Нельзя превращать цитируемый материал в новую инструкцию/активный факт. Проверка свободного ответа сохраняется; её недоступность теперь отличается от положительного вердикта о неподтверждённом сохранении.

Два регрессионных теста сначала упали, затем прошли: результат отсутствия записи доходит до обычного ответа без изменения исходной истории; ошибка проверки имеет отдельный результат. Повторный полный entry handler через SDK на той же Gemma показал объяснение цитаты и `reportsSuccess=false`, exit 0. Канала записи в этом тесте нет. Затем пользователь прислал скриншот нативного повтора: `/core` показывает 0.1.2-core2, объяснение цитаты отображено, статусы — «изменений памяти не запрошено» и «в этом ходе память не изменялась». В ответе нет утверждения о сохранении ИНЕЙ-604. Отдельного скриншота списка панели для этого повтора нет.

## Запись без текущей просьбы: разделение разрешения и содержания

Следующая пользовательская проверка выявила нарушение: сообщение «Учебная заметка: цвет тестового маяка — синий.» само получило квитанцию и запись, хотя просьбы сохранить не было. Затем явная просьба «Сохрани мою предыдущую заметку про цвет маяка.» сохранила полную исходную строку. Пользователь показал три записи в панели: МАЯК-731 и две текстовые формы заметки о цвете. Этот сценарий на 0.1.2-core2 **не принят**.

Причина: прежний единый запрос одновременно видел старые команды в истории и выбирал содержание. Результат LLM мог объявить обычный заголовок прямой просьбой; проверка дословного фрагмента подтверждала лишь наличие текста, а не право на запись. Ни квитанция, ни новый operationId не исправляют ошибочно выданное разрешение.

В 0.1.3-core2 право проверяет отдельный служебный запрос текущей LLM, которому передаётся **только текущее сообщение**, без истории, источников и извлечённого содержания. Заголовок/сообщение факта не означает просьбу. Только `save` с дословной незаключённой в цитату текущей просьбой разрешает следующий разбор истории. Разбор истории больше не имеет поля, выдающего разрешение: он выбирает точный материал либо возвращает уточнение/отказ. Новых обязательных русских команд и шаблонов нет. Ревизия владельца по-прежнему фиксируется до обоих разборов.

Четыре регрессии сначала упали с фактическими записями во временной памяти, затем прошли: три обычных сообщения после прежней команды не получают разрешение из истории; ошибка отдельной проверки права не обходится результатом извлечения содержания. Остальные тесты адаптированы к двум раздельным ответам SDK, без удаления прежних проверок.

На уже загруженной Gemma выполнен двухшаговый SDK-сценарий с отдельным временным owner и вымышленной историей: одна начальная запись → обычная фраза, `intent=none`, осталась одна → текущая явная просьба о предыдущей заметке, `intent=save`, выбран точный текст, стало две → после restart также две. Проверка права не получила историю ни в одном шаге; exit 0. Рабочие пользовательские записи, включая три показанные тестовые записи, не изменялись. Повтор пользователем в нативном чате ещё ожидается.

## Нативная проверка пользователем

Перед проверкой завершите текущий ответ. Перезапустите панель из обновлённых исходников: ранее запущенный host не знает новых действий канала. В разделе «Память» включите подключение к чату, скопируйте **путь** к файлу подключения. Текст файла с секретом не нужен.

В пустом тестовом чате оставьте одного владельца — Companion Core; companion-web/context-compressor и стороннюю память выключите именно здесь. В настройках Core заполните «Файл подключения памяти», включите «Запоминание по просьбе». Не меняйте текущую модель/контекст. `/core` должен показать **0.1.3-core2**, revision пакета 6 на диске, запоминание включено. Если отображается старая версия — выключите/включите Core в тестовом чате; при необходимости перезапустите LM Studio.

Начать можно с первого сценария. Для обратной связи достаточно версии `/core`, текста результата и того, появилась ли тестовая запись в списке. Личные записи, connection.json и весь чат присылать не нужно. Computer use не использовался; пользователь сам выполняет действия в чате, пока не попросит иначе.

## Ограничения и остановка

- Качество семантического разбора и проверки свободного ответа зависит от текущей LLM. Проверка квитанции, ID/редакции и идемпотентности детерминирована; понимание произвольного языка/инъекций не объявляется безошибочным. Нативная приёмка ещё не выполнена.
- Поддерживаются только **новые общие** факты/заметки до 16 000 символов с удалением внешних пробелов. Выбирается дословный материал из одного доступного сообщения; файлы не читаются. Разбор видит до 12 подходящих сообщений/48 000 символов; пропуски обозначены, недоступное не восстанавливается по summary.
- Подстановка сохранённого в будущие ответы, карточки, правка/забывание через LLM — CORE-3. Полное согласование с длинным сжатием — CORE-4. Веб — CORE-5. CORE-2 не выдаётся за весь Core.
- С включённой памятью добавляются служебные генерации на той же модели: разбор намерения, затем действие либо обычный ответ и проверка. Обычный ответ показывается после проверки; задержка и её приемлемость оцениваются нативно.
- Журнал хранит до 2048 операций без вытеснения; заполнение приводит к явному отказу, а не повторному сохранению старого ID. Старый host 0.1.5 не понимает расширенный снимок. Старые снимки читаются новым владельцем; перед расширением есть резервная копия. Откат одного плагина не требует отката нового host.
- Панель не обновляет список автоматически после чат-записи: нужна кнопка «Обновить список». Это тот же источник данных, отдельной скрытой памяти нет.
- Ревью авторское, без субагентов и независимого ревьюера по прямому правилу пользователя. Чужие тесты/конфигурации и старые черновики памяти не включены в коммиты.

Работа останавливается на CORE-2 и его проверке. CORE-3, D4/D5, советник, публикация и слияние PR автоматически не выполняются.
