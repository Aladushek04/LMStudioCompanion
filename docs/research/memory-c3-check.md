# C3: подстановка общей памяти перед ответом

Дата: 2026-10-30. Выпуск панели 0.1.3. Выполнен только C3; C4 и C5 не начаты.

Единственный владелец C1 обслуживает панель и локальный канал чтения. Плагин не открывает memory.json или прежнюю memory.db. Подключение включается явно в панели; отдельно включается использование в нужном чате. Обычный recall не вызывает генерацию, не загружает модели и не записывает факты. Запрос и содержимое памяти не журналируются.

Выбраны Windows named pipe и отдельный файл подключения с правами только текущего пользователя. Полный управляющий токен панели плагину не передаётся. Канал проверяет HMAC обеих сторон до передачи запроса, ограничивает размеры сообщений/число соединений/время ожидания, допускает только recall и подтверждение переданных ID. Включение переживает restart; секрет меняется. Параметры Node IPC сверены с [официальным описанием](https://github.com/nodejs/node/blob/main/doc/api/net.md). Другие ОС в этом выпуске не поддержаны каналом памяти.

Без подтверждённого стабильного chatScopeId доступны только global. Проектные записи можно хранить и редактировать в панели, но они не подставляются; выбор проекта панели не выдаётся за привязку чата. Временные записи не становятся постоянными. Эти ограничения видны в панели и настройке плагина.

Подбор — лексический TF-IDF с лёгким приведением русских окончаний, без embedding-модели. Область и deletedAt фильтруются до ранжирования. Закреплённые записи доступны при коротком вопросе; обычные требуют совпадения слов. Размеченный до реализации набор — tests/fixtures/memory-recall-ru.ts: **10/10** ожидаемых записей в top-5, при требовании минимум 8/10. Это небольшой синтетический набор, а не оценка всех русских формулировок или семантического поиска.

Подстановка содержит не более пяти целых записей и 1024 токенов. Текущая просьба/явные материалы имеют приоритет; явное веб-чтение получает место первым, закреплённые предпочтения — раньше дополнительного поиска, обычная память — последней. Проверяется полный шаблон истории действительным токенизатором выбранной модели. Сохраняется резерв ответа max(2048,15% контекста) плюс 1024 запаса. Запись не режется посередине; пропуски из-за лимитов видны. Веб-план вычисляется из исходного запроса, не из добавленной памяти. Вложения сохраняются копией сообщения. Владелец генерации остаётся прежним.

Перед возвратом препроцессора владелец проверяет ID/revision против текущей памяти. Поздняя ручная правка или удаление останавливает устаревшую подстановку. Следующий ход читает текущую редакцию. После передачи контекста уже идущая генерация не переписывается. Удаление также не стирает старые ответы и summaries.

Статус показывает ID, revision, причины и фактически переданное количество. Это не доказательство того, что модель опиралась на каждую запись. Последняя метаинформация доступна после кнопки проверки в панели, хранится только в RAM и сбрасывается при restart. Нет содержимого записей, текста запроса или автоматического увеличения accessCount.
