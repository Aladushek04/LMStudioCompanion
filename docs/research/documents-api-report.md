# D0: файловый API и граница адаптера документов

Дата: 2026-10-30. **Завершено исследование D0; обработка документов в продукте ещё не подключена.** [Разбивка D](../plans/04-documents-stages.md), [машинные результаты](../../reference/documents-d0-check.json).

## Среда и исходники

LM Studio **0.4.27.0**, проектный SDK **1.5.0**, context-compressor **0.8.3 / revision 27**. Уже загружена google/gemma-4-12b-qat, embedding не загружена. До/после probe список загруженных моделей одинаков; generate/respond/model/load не вызывались. Чаты, личные файлы, конфигурация и данные плагинов не читались.

Установлен lmstudio/rag-v1: manifest **revision 8**, package **1.0.0**. В package указана зависимость SDK **1.4.0**, но в его node_modules фактически SDK **2.0.0**. Это разные факты; текущий проект не обновлялся до 2.0.0 на основании установленного плагина. Проверки ниже выполнены с собственным закреплённым SDK 1.5.0.

В package rag-v1 заявлена **ISC**, отдельного LICENSE/COPYING в установленной корневой папке нет; README — стандартный scaffold. Полнота лицензионного уведомления для fork не установлена. **Выбран самостоятельный адаптер публичного SDK, без копирования кода rag-v1 и без изменений его установки.** Если позже понадобится fork, сначала проверить полный текст лицензии/уведомлений у первоисточника.

По исходникам rag-v1 регистрирует withPromptPreprocessor, использует файлы текущего сообщения и истории, выбирает полный текст или retrieval. Retrieval сам запрашивает nomic-ai/nomic-embed-text-v1.5-GGUF через embedding.model; этот путь не запускался. Defaults: limit 3, affinity 0.5 — эвристика, не вероятность истинности. Пустая выдача превращается в просьбу модели предупредить и ответить по общим знаниям; готового строгого режима это не даёт. Официально опубликованный [исходник rag-v1](https://www.lmstudio.ai/lmstudio/rag-v1/files/src/promptPreprocessor.ts) также показывает загрузку embedding и такое поведение; вывод о конкретной установке основан на локальных исходниках.

## Фактические проверки

Скрипт scripts/check-documents-api.mjs загружает только четыре фиксированные синтетические fixtures из tests/fixtures/documents, сверяет хеши и ограничивает каждый вход 64 KiB. Один operation deadline 8 секунд, watchdog probe 60 секунд; эти числа — ограничения исследовательского скрипта, не спецификация сервера. После проверок собственный SDK-клиент закрывается.

PDF независимо проверены pypdf: два текстовых листа с обоими маркерами; у скана одна страница, ноль извлечённых символов и одно изображение. Три страницы отрисованы Poppler и просмотрены; у текстового PDF читаемые заголовки/строки, у скана — только изображение. Poppler предупредил о недоступных Symbol/ArialUnicode; на используемые Helvetica и изображение это визуально не повлияло. Генератор fixtures — scripts/make-documents-fixtures.py; библиотеки взяты из bundled runtime, зависимостей проекта не добавляли.

Проверка времени жизни относится **к временным SDK-загрузкам нашего клиента**. Это не доказательство такого же жизненного цикла файлов, прикреплённых пользователем в нативном чате: они принадлежат другому владельцу и требуют проверки D4. Восстановление собственного истёкшего идентификатора использовало deprecated FileHandle constructor только в probe, не как проектный контракт.

## Решение для D1–D4

1. **D1:** самостоятельный адаптер поверх проверенного parseDocument с builtin backend. Оставить SDK 1.5.0; обернуть deprecated API в одном месте и проверять доступность. Не подменять отсутствующий backend загрузкой нового парсера, облаком или отдельной моделью. TXT/PDF с пустым текстом — unreadable, ошибка — error; ready означает готовый текст, а не готовый семантический поиск.
2. **Идентичность:** собственный document ID и SHA-256 выбранных исходных байтов; имя только для отображения. Область и версия извлечённого текста должны учитывать parser version. Не использовать временный SDK identifier как постоянный ID библиотеки, не считать имя уникальным.
3. **Locators:** в D1/D3 — имя, устойчивый номер/диапазон фрагмента извлечённого текста и его версия. Не показывать физические страницы по догадке, даже если текст явно разбит заголовками. Явная глава/раздел допустимы после проверенного определения границ; неизвестный раздел требует уточнения. Нативные citations не обещать до успешного retrieval и проверки D4; собственный просмотр фрагмента в D2 не зависит от них.
4. **Подбор:** до embedding сначала проверить лексический baseline на размеченных вопросах D3; это не собственный vector-store и не обещание семантического качества. Native retrieval остаётся отдельной capability с явной моделью, ресурсами и проверками, без автоматической nomic-загрузки.
5. **Привязка:** текущие проверенные вложения/выбор действуют в рамках конкретного хода. Панель не задаёт глобальный набор для всех чатов. Хранить выбранные bytes/извлечённый текст только у явного владельца с ограниченным сроком; не сохранять голые temporary handles для восстановления после disconnect. Повторное использование файлов истории и срок жизни нативных вложений проверить в D4.
6. **Совместимость:** включать документы в существующем собственном препроцессоре, сохраняя ChatMessage и изображения; новый prediction-loop handler не регистрировать. Rag-v1 и адаптер Companion не должны обрабатывать один набор одновременно. Переключение единственного RAG-пути в D4 явное; в D0 ни один установленный плагин не выключался.
7. **Строгий режим:** данными управляет политика до генерации, а не просьба «не выдумывай» внутри текста. Для пустой выдачи, ошибки и исключения всех фрагментов бюджетом требуется подтверждённая остановка содержательного ответа. Веб B ранее показывал ошибку препроцессора без нового ответа, но это не отдельная приёмка документов. D4 проверяет настоящий пустой/ошибочный ход с компрессором; до этого strict-mode недоступен. Даже после этого отсутствие выдумок в каждом предложении при непустых источниках не гарантируется.

Таким образом D1 можно реализовать без новой модели: проверен конкретный путь получения текста. Постоянные библиотеки, successful native retrieval и полная строгая интеграция не объявлены готовыми.

## Предлагаемые начальные пределы D1

Это инженерный выбор для первого адаптера, **не измеренные пределы LM Studio**: до 5 явно выбранных файлов, 8 MiB на файл, 20 MiB суммарно; по одному разбору за раз; UTF-8 TXT с BOM/без и текстовый PDF; 30 секунд на разбор, 90 секунд на набор; не более 250 000 символов извлечённого текста на файл до подбора по токенному бюджету. Превышение — явная причина отказа/ограничения, не тихое усечение. Сначала проверить эти границы в D1; D0 проверял лишь маленькие fixtures. Клиентский timeout и ограничение входных байтов сами по себе не являются доказанным лимитом работы/памяти native backend.

Для токенного бюджета использовать tokenizer текущего источника модели и резерв ответа/tools из B/C. Если выбранный материал не вошёл, показывать причину и частичный охват отдельно от отсутствия данных. Параметры больших библиотек G не переносить на D1 автоматически.

## Воспроизведение и границы результата

При работающей установленной LM Studio на 127.0.0.1:1234: node scripts/check-documents-api.mjs. Скрипт не принимает путь пользовательского файла; child-mode предназначен только для проверки собственного upload. Итог без текстов файлов и локальных путей сохраняется в ignored data/documents-d0-live.json; копия фактов — reference/documents-d0-check.json.

Регрессионные тесты диагностик проверяют сохранение причины, удаление служебной рамки/stack и серверных путей. Полные результаты unit/typecheck/build и итогового ревью фиксируются в машинном отчёте. Тяжёлые live-тесты, генерация, embeddings, 26B, перезапуск LM Studio и установка новой версии SDK не выполнялись. D1 не начат; публичного релиза и изменения архива 0.1.5 нет.
