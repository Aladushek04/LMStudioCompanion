# Подготовка к вайбкодингу — Этап 0

**Дата:** 2026-11-03  
**Статус:** согласован, вариант B  
**Рабочая ветка:** `vibecoding-stage-0` в отдельном worktree

## Зачем

Проект хорошо документирован и имеет сильные контракты, но быстрые изменения через ИИ упираются в инженерные страховки:

- корневой `typecheck` и `npm test` не проверяют `conversation-engine`;
- CI отсутствует;
- нет линтера/форматтера;
- границы пакетов неформальны;
- `handler.ts` слишком велик для безопасных правок;
- версии продукта, Core и плагина расходятся;
- ссылки в релизном ZIP ведут на удалённую ветку.

Этап 0 закрывает первые четыре и последние два пункта. Разбиение `handler.ts` и общие API-схемы остаются на Этап 1.

## Цель

Сделать так, чтобы одна команда `npm run verify` давала честный ответ «проект цел», а ИИ мог понять границы модулей без чтения всей документации.

## Не входит

- CORE-3, карточки, новые функции памяти;
- изменения схемы памяти, чатов, настроек LM Studio;
- D4/D5 и документы;
- рефакторинг `handler.ts`;
- общие API-схемы панели и host;
- обновление major-зависимостей;
- публикация релиза.

## Ограничения

- Рабочий runtime — Node 24.22.2; Core дополнительно проверен на Node 25.5.0.
- CI использует Node 24.22.2.
- Не трогать незакоммиченные файлы исходного дерева.
- Не менять живую память, `data/`, `backups/`, чаты и настройки пользователя.
- Сохранять лицензию и авторство `conversation-engine`.
- Пользовательские тексты — на русском.
- Новых runtime-зависимостей нет; добавляется только dev-зависимость Biome.

## Рассмотренные подходы к форматированию

### A. Форматировать всё, включая Core

Плюс: единый стиль сразу.  
Минус: diff на ~10 тыс. строк, сложнее сравнивать с upstream, а `handler.ts` всё равно будет разбираться в Этапе 1.

### B. Форматировать код Companion, Core оставить до Этапа 1 — выбран

Плюсы: diff меньше, происхождение Core сохраняется, основной Companion-код становится читаемым.  
Минус: `handler.ts` остаётся плотным до Этапа 1.

### C. Только lint, без форматирования

Минимальный diff, но главная проблема читаемости остаётся. Не выбран.

## Решения

- **Biome** как форматтер и лёгкий линтер: быстрее и проще, чем ESLint + Prettier; не требует нового runtime.
- **Собственный `check-boundaries.mjs`** вместо dependency-cruiser: правила прозрачны, нет новой зависимости, легко объяснить ИИ.
- **GitHub Actions на Windows**: продукт Windows-only, E2E использует Edge.
- **Node 24/25 разрешены, CI на 24.22.2**: соответствует проверенному runtime; Node 26 блокируется с понятным сообщением.
- **Core исключён из массового форматирования**: сохраняем upstream-provenance; форматируем по мере выноса этапов.
- **Версия продукта** берётся из корневого `package.json` и подставляется в панель при сборке. Версии Core и плагина остаются отдельными и документируются.

## Риски и смягчение

- **Большой diff форматирования.** Отдельный коммит, Core исключён, логика не меняется, тесты после.
- **Node 24 обязателен.** `.nvmrc`, `engine-strict`, `check-node` дают понятную ошибку.
- **Перенос границ.** Только перемещение и re-export; полный прогон тестов.
- **CI медленный/нестабильный.** Кэш npm/pip, таймаут 20 минут, без живой модели.
- **Незакоммиченные файлы пользователя.** Работа в отдельном worktree; исходное дерево не трогается.

## Критерии готовности

- `npm run verify` проходит на Node 24.22.2.
- `npm run verify:full` проходит локально и в CI.
- Ни один production-импорт не нарушает матрицу границ.
- Форматирование Companion-кода выполнено одним коммитом; Core не отформатирован.
- Панель показывает `0.1.5`; релизные ссылки ведут на `main`.
- Документация обновлена; отчёт с числами приложен.
- Память, чаты, настройки LM Studio и `data/` не изменены.
