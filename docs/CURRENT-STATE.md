## Как работает persistent-memory

Установлен `khtsly/persistent-memory`, manifest revision 5, package 1.0.1, MIT по package.json. Основные файлы: `src/preprocessor.ts`, `src/toolsProvider.ts`, `src/storage/db.ts`, `src/retrieval/engine.ts`, `src/config.ts`.

1. Факты — отдельные строки SQLite в `~/.lmstudio/plugin-data/persistent-memory/memory.db`, если путь не переопределён настройкой. Веса Gemma не меняются.
2. Модель получает инструменты Remember, Recall, Search Memory, Forget, Memory Status. Сохранение через инструмент зависит от того, вызвала ли его модель.
3. Препроцессор подбирает несколько записей перед новым сообщением. По умолчанию максимум 5, есть ограничение длины. Текст добавляется к сообщению пользователя; это не магическая запись в системную память модели.
4. В текущем коде сообщения короче 10 символов проходят без автоматической подстановки. Автоматическое извлечение фактов запускается при длине от 30 символов, если настройка включена; ошибки могут проходить без видимого уведомления.
5. Области — общее, проект, временно. Временные записи живут в памяти процесса, не в SQLite. Активный проект задаётся строковой настройкой; строгую изоляцию проектов нужно проверить отдельно, не выводить её из описания.
6. Подбор основан на TF-IDF и эвристиках; это не полноценный семантический embedding-поиск. На русских перефразировках качество нужно измерять. README преувеличивает обязательность AI reranking: автоматический путь вызывает обычный retrieve.
7. AI-функции выбирают первую загруженную модель, а не обязательно выбранную в чате. В просмотренном helper таймаут ограничивает ожидание списка моделей, но не весь поток генерации. Нужны явный выбор модели, отмена и очередь.
8. sql.js загружает файл целиком в память и экспортирует его после операций. Ошибки persist подавляются. Два независимых процесса записи могут затереть изменения друг друга; новая панель не должна писать прямо в живой файл.

Итог для пользователя: «запомни» может сохранить факт, но текущий интерфейс слабо объясняет успех, причину выбора и отсутствие нужного факта. План 03 добавляет управление и наблюдаемость, а не дообучение.

## Как работает rag-v1

Установлен `lmstudio/rag-v1`, revision 8, SDK dependency 1.4.0, ISC по package.json. Основной файл `src/promptPreprocessor.ts`.

- Принимает прикреплённые к чату не-графические файлы через FileHandle и историю чата.
- Измеряет доступный контекст, парсит документы и выбирает полный текст либо retrieval. Само решение уже автоматическое.
- Использует `client.files.parseDocument`, `client.files.retrieve`, `ctl.addCitations`. Retrieval загружает `nomic-ai/nomic-embed-text-v1.5-GGUF`.
- Defaults: до 3 найденных фрагментов, фильтр score > 0.5. Это эвристические настройки, а не вероятность истинности.
- При пустой выдаче добавляет модели просьбу предупредить и затем ответить по знаниям. Для режима «только по документам» потребуется другой контролируемый результат.
- Постоянные библиотеки папок, наблюдение за изменениями и понятный обзор индекса в этом исходнике не реализованы. Их API нужно исследовать отдельно.
- Нельзя гарантировать номера PDF-страниц, если парсер/метаданные их не предоставили; тогда показывать файл и текстовый фрагмент.

## context-compressor

`rootmonster/context-compressor`, revision 27. Регистрирует `withPredictionLoopHandler`. Сам управляет генерацией, передаёт инструменты активной сессии, ограничивает объём результатов.

В `src/toolWrap.ts` уже есть `invalidToolRequestResult` и обработка исключений инструментов; `src/handler.ts` использует это при невалидном запросе. План 06 должен расширять и измерять существующее поведение, не дублировать бесконечный retry-loop.

Локальный SDK содержит `promptTemplate`, но поле deprecated; `raw` тоже экспериментальное с предупреждением «Do not use». Видимость таких полей не доказывает надёжное управление Gemma Thinking. План 02 начинается с проверки реального шаблона и поддержанного интерфейса.
