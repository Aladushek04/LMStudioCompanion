# C5: перенос памяти и итоговая приёмка — Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans. Только C5, без автоматического перехода к D.

**Goal:** Перенос выбранных постоянных записей из согласованной offline-копии с предварительным просмотром, резервной копией и безопасным откатом.

**Spec:** [C5](03-memory-stages.md), [DESIGN](../DESIGN.md), [схема C0](../research/memory-compatibility.md).

**Architecture:** Единственный владелец C1 выполняет одну атомарную пакетную запись. SQLite-снимок версии 2 читается только из переданных байтов в RAM через проверенный node:sqlite.deserialize (Node >=24.16); файлы старого плагина приложение само не ищет. Поддержан также явно помеченный JSON обменный формат v2 для синтетических проверок. Исходные неизвестные поля сохраняются в metadata как исходный JSON. Session пропускается.

**Решения:** выбор offline-копии и подтверждение остановки старого владельца в панели; предварительный просмотр ничего не пишет. Пользователь выбирает записи; текущие/забытые импортированные ID не меняются и не оживают. Семантического объединения разных ID нет: выбранные новые записи проверяет пользователь. Резервная копия Companion и маркер импорта сохраняются до/вместе с атомарной записью. Откат доступен только до последующих постоянных изменений, сохраняет RAM-session и увеличивает revision. Исходный файл не меняется.

Пользователь сообщил, что старых записей нет: личная миграция не требуется. Приёмка выполняется только на синтетических копиях; это не заявляется как перенос личных данных.

- [ ] RED→GREEN parser: поля/неизвестные значения/связи/области/повреждение/SQLite v2; fixture memory-v2.json.
- [ ] RED→GREEN owner: атомарный импорт, повтор/ручная правка/delete/restart, backup/сбой/отмена/rollback/устаревшее окно; отдельный коммит.
- [ ] API и экран: выбранный файл до 8 MiB, offline-подтверждение, preview в RAM на 10 минут (не более двух), выбор записей, подтверждение, откат; защиты/браузер/ошибки.
- [ ] Полный набор, tsc/build, одно независимое ревью, исправления RED→GREEN, итоговый комплект и отчёт C. Минимальная проверка импорт→recall→rollback на текущей 12B, без 26B и тяжёлой повторной компрессии. Коммиты/push; остановка перед D.

Фокус: активный источник не открывается напрямую; временные записи не попадают в собственные backup; неизвестная область не становится global; повтор не отменяет ручную правку/удаление; ошибка между backup и commit не разрешает ложный rollback; чужая/повреждённая копия не применяется; отсутствие стабильного ID чата по-прежнему ограничивает recall общей памятью.
