# Этап D — документы отдельными подэтапами

> **For agentic workers:** Use superpowers:executing-plans для одного заказанного подэтапа за заход. Шаги отмечать через `- [ ]`. Не переходить автоматически к следующему подэтапу. Это разбивка исходного плана 04; подробный план конкретного Dn готовить перед его реализацией по результатам предыдущих проверок.

**Goal:** Пользователь прикрепляет TXT или текстовый PDF, получает ответ по реально прочитанным фрагментам и может открыть источник.

**Architecture:** Переиспользовать существующие возможности LM Studio через отдельный адаптер Companion. Разбор файлов, подбор фрагментов и политика ответа разделены; обработка использует общий бюджет и реестр источников. В чате остаётся один владелец генерации; два конкурирующих RAG-препроцессора не включаются.

**Tech Stack:** Существующие TypeScript/Zod, локальный SDK LM Studio, React-панель, loopback API и Vitest. Парсер и retrieval backend выбираются после D0; их наличие, лицензию, ресурсы и поведение проверять, не подразумевать.

**Spec:** [Исходный план документов](04-documents.md), [DESIGN](../DESIGN.md), [приёмка](../ACCEPTANCE.md), [итог C](../research/stage-c-completion.md).

**Статус на 2026-10-30:** D0–D3 завершены: [исследование API](../research/documents-api-report.md), [адаптер D1](../research/documents-d1-check.md), [экран D2](../research/documents-d2-check.md), [подбор и бюджет D3](../research/documents-d3-check.md). D4 отложен, D5 впереди. Документы доступны в панели, к действующему чату ещё не подключены. [Текущее состояние](../STATUS.md).

## Границы и общие правила

- Первый выпуск D: прикрепления **TXT и текстового PDF**. OCR сканов, полноценное понимание таблиц и картинок PDF не входят; отсутствие извлечённого текста явно показывать.
- Постоянные библиотеки папок, обход каталогов, слежение за изменениями и постоянный индекс — **этап G / задача 3 плана 04**. Их исследование в D0 не является их реализацией.
- Два сценария из решения пользователя: автоматический подбор по вопросу и явное ограничение файлами, главами, разделами или страницами. Автоматика ищет только внутри заданной области. Страницы допустимы лишь при подтверждённых metadata; неизвестный раздел не заменять поиском по всему файлу молча.
- Приоритет контекста: материалы текущего запроса → закреплённые предпочтения → дополнительный поиск и обычная память. Оставлять резерв ответа, учитывать инструкции, историю и tools; совместимость с context-compressor сохранять.
- Документы — данные, не управляющие инструкции. Не выполнять их команды, не сохранять содержимое автоматически как личные факты. Наличие source_id не доказывает истинность ответа.
- Отмена распространяется на чтение, разбор и retrieval; поздний результат не подменяет новый запрос. «Готово» означает конкретную завершённую операцию, а не только успешное добавление файла.
- Использовать общие OperationResult, TurnContext и SourceRecord из packages/core/src/contracts.ts. Предлагаемые в плане 04 API — внутренние контракты, а не обещанные методы LM Studio. Дополнения согласовать схемами и тестами до использования.
- Существующие Host/Origin/token-защиты сохранять. API не читает произвольный путь из URL или текста модели. Только явно выбранные пользователем файлы/проверенные handles; идентичность включает содержимое, а не одно имя.
- Не подменять отсутствующий стабильный ID чата глобальным выбором документов в панели. Привязку набора к текущему ходу и отзыв выбора доказать в D0/D4; файлы одного чата не должны попадать в другой.
- Чужие установленные плагины не редактировать; адаптер или отдельный лицензированный fork. Изменение активного RAG делается явно, без молчаливого отключения других инструментов.
- Исходные файлы не изменять. Личные документы и чаты для тестов не читать; синтетические фикстуры не включают секретов. Сырые документы, локальные пути и токены не писать в журналы и отчёты.
- Не добавлять облачные сервисы, embedding-модель, собственный vector-store или второй генератор молча. Проверять необходимость и ресурсную стоимость; не перезагружать текущую модель и не запускать 26B ради этого плана.

## Порядок выполнения и проверки

Один заход — **D0 → остановка**, затем по отдельному поручению D1, D2, D3, D4 и D5. Каждый подэтап даёт собственный результат, проверки и отчёт; выполнены пункты D0–D3; дальнейшие подэтапы требуют отдельного поручения.

Во время реализации использовать существующий запуск Vitest с конкретным файлом тестов подэтапа; полный набор — когда появились изменения поведения, на итоговой приёмке и после существенных исправлений. Для текущего изменения документации достаточно проверки ссылок, границ этапа и diff: LM Studio, модели и пользовательские файлы для составления этой разбивки не нужны.
